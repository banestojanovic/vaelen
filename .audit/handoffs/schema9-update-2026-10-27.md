# Schema 9 signed app update handoff

`Scripts/vaelen-dev-update` now accepts a live schema 8 database when the installed embedded Core also reports schema 8 and the candidate source and embedded Core both report schema 9. The updater rejects an installed Core/live DB mismatch and a candidate below the live DB before it requests GUI shutdown. It no longer accepts an unavailable CLI because the installed Core has a hard-coded stale schema.

The compatibility state is the tuple `(live schema, installed Core schema, candidate source schema, candidate embedded Core schema, migration outcome)`. The early gate checks the first three values. The signed build then checks that candidate embedded Core matches candidate source. After launch, the updater records the live DB schema in `schema-after.txt` and writes `target-reached`, `pre-migration`, or `advanced` to `migration-outcome.txt`. Acceptance requires the target schema and preserves CLI status, Core ownership, route inventory, service readiness, signature, team, and app tree checks.

The online SQLite backup remains recovery evidence. The updater never restores or replaces the live database. On failure after schema advancement, the error says the prior app may not read the DB; use the retained evidence and app backup for manual recovery decisions. This change does not run a migration itself or prove that the canonical installed app can safely roll back after Core has advanced the DB.

The updater now supports an isolated signed-app fixture when both `VAELEN_DEV_UPDATE_TEST_MODE=1` and `VAELEN_DEV_UPDATE_TEST_ROOT=/private/tmp/<unique-name>` are set. The root must already be a real directory owned by the current user and contain a regular owned `.vaelen-dev-update-test-fixture` file whose exact contents are `vaelen-dev-update-test-fixture-v1` followed by a newline. It derives the fixture home at `<root>/home`, leaving the updater shell's `$HOME` unchanged; app, support, update evidence, CLI-link paths, Foundation's user home, and Release DerivedData all use that root. Before any app shutdown or filesystem mutation, fixture mode rejects any running Vaelen GUI or Core process, including processes under alternate app bundle names. It rejects symlinks at every existing fixture home, support, artifact, CLI, state, runtime, socket, and app path component or leaf. The promoted fixture app executes `Contents/MacOS/Vaelen` directly under `/usr/bin/env -i` with fixture `HOME` and `CFFIXED_USER_HOME`, explicit test support-root variables, and `VAELEN_TEST_ALLOW_CORE_START=1`. It does not use LaunchServices environment forwarding. Ordinary isolated UI fixtures still refuse to start Core. The updater opt-in starts only the bundled Core and skips privileged-helper registration. Core inherits the GUI environment. Acceptance requires the directly launched GUI PID, exactly one GUI and Core, the fixture socket and its verified owner, and migration of the fixture DB. Process identity accepts the `/tmp` spelling of the owned `/private/tmp` fixture prefix only in test mode. The updater CLI and readiness checks inherit fixture paths. Partial or malformed opt-in is rejected before filesystem mutation. Production paths and launch remain unchanged when neither variable is set.

For a manually prepared fixture, create a unique direct child directory under `/private/tmp`, create the marker with `printf 'vaelen-dev-update-test-fixture-v1\n' > "$root/.vaelen-dev-update-test-fixture"`, populate its `home/Library/Application Support/Vaelen` state and `home/Applications/Vaelen.app`, then run the updater with both opt-in variables exported. The contract test checks path validation, executable alias identity, rejection of a different GUI PID, and actual child environment inheritance using a harmless shell executable. It does not launch Vaelen or perform the signed update.

The independent review identified three remaining isolation gaps after the incident. Fixture exports now run before the readiness helper is sourced, because that helper captures its CLI and intents paths immediately. The contract seeds distinct host and fixture intents and executable stubs in temporary directories, then runs the updater's actual setup and readiness function. It observes only the fixture `routing status` command.

Core now selects `UnavailablePrivilegedDNSHelper` and `UnavailableStandardPortsPrivileged` whenever the explicit isolated support root is active. This takes precedence over the development privileged DNS flag. Both adapters reject acquisition and restoration. Their inspections read fixed resolver/PF files in user space and never create a privileged XPC connection. Production adapter selection is unchanged. The app also refuses helper registration at the registration entry point for isolated support roots, including explicit Settings actions. The updater Core-start flag bypasses registration only for the isolated Core-start path; ordinary Settings fixtures still cannot start Core.

Fixture validation explicitly checks both SQLite databases and their `-wal` and `-shm` sidecars. It also rejects every existing symlink under the support tree before launch or mutation. Reviewing Core layout paths found nested writable configuration, instance, runtime routing, TLS certificate, log, and cache paths beyond the original top-level list. Recursive rejection covers these leaves and package descendants. Prepared fixtures must use real copied support files and directories. Contracts exercise symlink escapes for both databases, every sidecar, service intents, and representative nested writable leaves. Validation repeats before the direct fixture launch. Fixtures are owned, quiescent test trees; these checks do not claim protection from concurrent hostile path replacement.
