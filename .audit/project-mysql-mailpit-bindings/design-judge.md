# Architect cross-judge verdict

Recommend **candidate B as the base**, with the bounded corrections/grafts below. B hides complete V2 binding policy behind one facade, makes singleton stop unavailable in its private adapter, and derives native eligibility from Core's assessed inventory. A is the smaller relocation, but leaves more operation sequencing in the dispatcher, adds catalog refresh hooks at many entry points, and asks native code to fetch separate global statuses. Both reject the V2 legacy-observation bypass for the same sound reason: schema-9 claims require a catalog parent, and bypassing it splits durable ownership.

This is the single design cross-judge. I read both candidates end to end, the grounding and task predicate, the architect red flags, the Codex mapping, and the arena skill. This verdict does not establish implementation correctness or runtime acceptance.

## Valuable grafts and required corrections

1. **Graft A's module-owned exact-start adapter into B's singleton adapter boundary.** A, **Shape → Data structures first / Module-owned identity rules**, names `startProjectService(expected:)` and puts next-launch validation and post-start identity checks inside the existing service source file. B's **Inspect and activate**, step 7, requires equivalent checks but mostly sketches ordinary `start()` from the facade. Keep B's no-stop singleton capability while adopting A's precise placement of package, configured-port, path and process checks. Do not add a second process launcher.
2. **Keep A's stricter omitted-version condition.** Grounding, **Boundary constraints**, permits omission only if current catalog identity supplies the local package. A, **Usage / Shape**, follows that. B, **Data structures first**, instead says the adapter's full live record suffices, including prospective uncataloged entries. Restrict B: prospective inventory may offer an explicitly pinned exact package, and adoption writes that pin; a portable declaration that omits version cannot activate from a prospective live descriptor alone. It needs a verified current persisted catalog identity. This correction uses A's rule without requiring A's read-triggered catalog refresh architecture.
3. **Carry A's explicit global-intent and downgrade caveats into B's rationale.** A, **Lifecycle → Intent/restart**, says V2 claims must not set global service intent and do not add claim-driven boot startup. A, **One-way doors and migration**, acknowledges older binaries do not enforce the new removal guard despite readable schema. These are useful compatibility limits, not extra functionality.

## Inaccurate or risky claims to resolve

### Mailpit `dataDirectory`

A, **Shape → Data structures first**, deliberately stores the `messages.db` **file** in a field named `dataDirectory` and describes the field as having a broader location meaning. That is a proposed semantic change, not an established catalog contract. `ServiceInstanceRecord` currently validates an absolute string, so the constructor does not prohibit it, but existing inventory fixtures use a directory (`Tests/VaelenIPCTests/ServiceInstanceInventoryTests.swift`, `/data/mailpit`). Current module evidence is unambiguous: `MailpitModule.instancePaths()` owns both the default instance directory and its `messages.db`; `instanceDatabasePath()` exposes the latter. The module's status DB path does not prove the catalog field means file path.

Prefer B's **Data structures first** distinction: persist the actual default instance directory, carry/check the exact database file in the module-minted live storage snapshot, and never derive authoritative module paths in the facade or UI. B's claim that this “keeps” established Mailpit catalog semantics is slightly too strong: this feature is establishing the production singleton projection, and existing fixtures show convention rather than a hard type invariant. Its shape nevertheless preserves the field's directory meaning and the actual DB invariant without a data move. A file-in-directory-field choice would need an explicit repository-wide contract justification that the candidate does not provide.

B's path protection must remain an invariant at every start and healthy observation. Comparing only the persisted directory would miss an unexpected DB filename; the live `DefaultProjectStorage.mailpit` and module process-argument checks are therefore required, not optional display metadata. A future change of the module-owned filename requires deliberate migration policy, as B already states in **One-way doors and migration implications**.

### Read-only inspection is qualified

B, **Catalog materialization without mutating plan**, correctly eliminates catalog writes on report, but “Inspection and plan are read-only” is too literal if implemented by calling current status methods. Current `MailpitModule.status()` can remove stale process metadata and reap/reset owned child state; MySQL status can clear exited runtime artifacts. Describe this as no provisioning, claim/catalog mutation or lifecycle action added by inspection, while preserving established module status cleanup. A already admits catalog metadata writes during report; its “metadata refresh never creates” claims should distinguish the refresh operation from any pre-existing status cleanup it calls.

### Retirement versus atomic claim replacement

B, **Inspect and activate**, step 5, retires old claims/runtimes before step 6's atomic replacement, yet step 6 says previous claims survive a concurrently changed expected row. That statement is only true of claims still present when the SQL transaction begins. A similarly defers to existing retirement logic in **Lifecycle → Up**. Specify that validation failures leave desired replacement uncommitted, start failures retain committed desired claims, and prior successful isolated stops/retirements can be partial effects. Do not advertise an all-or-nothing runtime transition. This is a wording and implementation-contract correction inside the chosen design, not a reason to invent another coordinator.

### Removal transaction guarantees

B's exclusion is stronger than A's actor-only guard, but a SQLite rollback cannot undo service intent writes, process stops or package deletion; B acknowledges process/package partial effects. Also include durable intent in that statement. Keep callbacks synchronous, bounded by existing stop limits, free of nested repository transactions, and free of asynchronous/network work. Verify actual journal/busy behavior before promising readers remain unaffected: `BEGIN IMMEDIATE` establishes write exclusion, not a universal reader-performance guarantee. Tests across two repository connections are valuable here. A's “never hold a SQLite transaction while starting/stopping” is an alternative tradeoff, not evidence that B's deliberate bounded removal exclusion is invalid.

### Scope and representation risks

B's facade is only deeper if existing V2 PG/Valkey orchestration actually moves into it. Leaving the old dispatcher route beside the facade would create two ways to activate/release and defeat its main advantage. Its fallback for old PG/Valkey observation fixtures (**Data structures first**) must not become a second production decision path. Internal snapshot constructors are module access control, not cryptographic provenance; correctness still comes from the owning modules and revalidation, as both candidates require.

## Convergence and red-flag disposition

The candidates **materially converge on the core architecture**: existing module-owned default singleton identities, real schema-9 catalog claims, exact package/endpoint/path matching, module readiness, no implicit MySQL initialization, no external-process adoption, release-only singleton down, and claim-protected removal. Their separately considered V2 legacy-only path loses in both. This is not strong evidence for two different ownership models; the meaningful alternatives are read-triggered catalog reconciliation with dispatcher orchestration (A) versus prospective read-only inventory with transactional materialization and one policy facade (B).

B has the stronger red-flag result: less caller sequencing, no generic singleton stop, one native eligibility source, and private closed adapters. Its extra facade is justified by the complete policy it hides. A's simpler file footprint does not compensate for refresh hooks and split native status collection. Accept B with the limited A grafts above; reject A's Mailpit field reinterpretation and avoid grafting its refresh hooks or stop-capable uniform driver into B. No third design is proposed.
