# Vaelen verification map

These journeys form the verification map. A recipe is coverage only after a recorded execution. Read the entry for the changed behavior before selecting a focused check.

| Journey | Automated production entry point | Isolated or simulated boundaries | Manual GUI review | Not yet verified by this skill |
| --- | --- | --- | --- | --- |
| [Review and apply project adoption](project-adoption.md) | Core project, route-intent, service catalog, and live-route reads; actual `val project adopt` preview/apply child through private Core | Project fixtures with manifests, composer/package metadata, redacted `.env` facts, malformed/oversized files, route ownership/TLS cases, and isolated SQLite | Adoption UI and installed app acceptance remain manual | Herd settings import and installed-app adoption acceptance |
| [Activate a project environment](project-environment-lifecycle.md) | Actual `val project adopt`, `up`, and `down` children through private Core for HTTP and HTTPS PHP routes; `up/down/up` and real FPM/Caddy responses. Actual `val project up/down --json` child also covers exact PostgreSQL claims. | Temporary SQLite/project roots, copied read-only installed Caddy/PHP packages, injected DNS/PF/trust observations, generated PostgreSQL package, isolated Core/runtime, route mutation race | Native Settings and installed-app project controls remain manual | System DNS/PF/trust, Valkey/MySQL/Mailpit project bindings, restart/update recovery, installed app |
| [Persist service instances and claims](service-instance-catalog.md) | `ServiceInstanceRepository`, schema 9, and actual `val service instances` child against private Core | Temporary SQLite databases, migration fixtures, all five service kinds, multiple projects, and manual/project owners; no service process is started | No GUI or live service process | Restart recovery, update/removal safety, Valkey lifecycle |
| [Manage exact service instances](service-instance-lifecycle.md) | Actual `val service postgresql` and `val service valkey` children through private Core, with package archive verification and live process checks | Isolated SQLite, support roots, dynamic loopback ports, extracted local generated packages | Native service Settings remain manual | End-user package distribution, signed release, authenticated provenance, macOS 14, project Valkey bindings, update recovery, installed app |
| [List linked projects](links.md) | Real `val links` child, Unix socket, Core dispatcher, SQLite | Six seeded projects; disabled router, DNS, TLS trust, privileged ports | Linked-project GUI remains manual | Installed app, real routing, full PHP-FPM, CLI link creation |

| [Update PHP](php-update.md) | Dispatcher and socket lifecycle tests exist | Cached real PHP pair, private roots, router doubles | Update GUI remains manual | Not executed by the initial proof; cache required |

| [List managed service versions](service-versions.md) | Actual `val service versions` child for both types through private Core; native typed JSON payload comparison | Empty temporary package layout; no MySQL or Mailpit process and no service operations | No GUI interaction | Installed-app integration, package installation, live package or service health |
| [Manage a named PostgreSQL instance](service-instance-lifecycle.md) | Actual `val service postgresql` and `val project up/down` children through private Core; generated package archive verification; live PostgreSQL init, health, graceful stop, and non-destructive remove | Isolated SQLite catalog, support root, dynamic loopback port, and extracted package fixture | No GUI interaction | End-user package acquisition, signed/notarized release, repeatable PostgreSQL build, macOS 14, update, and Valkey |
| [View managed logs in the app](managed-logs.md) | Injectable viewer state model with controlled asynchronous replies | Fake Core client; race and state mapping tests | Window interaction, clipboard integration, and light/dark appearance remain manual | Live managed logs and GUI rendering |
| [Manage local HTTP proxies](local-http-proxies.md) | Actual `val proxy` child with private Core socket, restart persistence, official isolated Caddy forwarding, and redirect refusal | Fake router for CLI lifecycle; separate real Caddy with owned local upstream and loopback redirect pair | Installed Settings add/remove journey accepted; Open and Copy URL actions remain manual | Successful upstream forwarding in installed UI |

The initial proof executes only the links success, controlled mismatch, and owned-child timeout checks. Supplemental runs must record exact commands, status, selected and passed counts, and skips. A skipped prerequisite or zero matching tests is not success. `docs/cli/herd-parity.md` lists intended counterparts, not evidence that they were exercised.
